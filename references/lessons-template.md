# 经验教训模板

此模板由 autodev-skill-builder 自动生成，用于生成的 Skill 记录经验教训。

---

## 使用说明

当用户对你的工作进行修正时，必须使用此格式记录经验教训。

### 记录格式

```markdown
### YYYY-MM-DD: {简短描述}

**问题**：{描述发生了什么问题}

**根因**：{分析为什么会发生}

**规则**：{写出避免重复的规则}

**示例**：
- ❌ 错误做法：{错误示例}
- ✅ 正确做法：{正确示例}
```

### 记录要求

1. **立即记录**：用户修正后立即记录，不要拖延
2. **写出规则**：不只是描述问题，要写出可执行的规则
3. **包含示例**：用对比示例展示正确与错误做法
4. **避免责备**：关注如何改进，而不是错误本身

## 示例教训

### 示例 1：边界条件检查

```markdown
### 2024-01-15: 未检查边界条件

**问题**：修改配置后未验证空值情况，导致服务启动失败。

**根因**：只关注了正常流程，忽略了异常路径。

**规则**：修改配置相关代码时，必须验证空值和边界条件。

**示例**：
- ❌ 错误做法：直接使用 `config.value`
- ✅ 正确做法：`config.value if config.value else default_value`
```

### 示例 2：依赖导入

```markdown
### 2024-01-20: 忘记导入依赖模块

**问题**：添加新功能后，忘记在文件顶部导入新的依赖模块。

**根因**：只关注了实现逻辑，忽略了模块依赖。

**规则**：添加新功能时，同步检查并更新导入语句。

**示例**：
- ❌ 错误做法：直接使用新类而不导入
- ✅ 正确做法：先添加 `from module import NewClass`
```

### 示例 3：测试覆盖

```markdown
### 2024-02-05: 新功能缺少测试

**问题**：实现新功能后未添加对应的测试用例。

**根因**：认为功能简单不需要测试，忽略了回归风险。

**规则**：任何新功能实现必须包含对应的测试用例。

**示例**：
- ❌ 错误做法：只实现功能，不写测试
- ✅ 正确做法：先写测试用例，再实现功能
```

### 示例 4：日志输出

```markdown
### 2024-02-10: 错误日志信息不明确

**问题**：验证失败时，日志只输出"失败"，无法定位问题。

**根因**：没有在关键位置添加详细日志。

**规则**：在验证流程的关键节点添加清晰的日志输出。

**示例**：
- ❌ 错误做法：`print("验证失败")`
- ✅ 正确做法：`print(f"验证失败: 步骤={step}, 错误={error}")`
```

### 示例 5：临时补丁

```markdown
### 2024-02-18: 使用临时补丁而非修复根因

**问题**：遇到错误后只是修改了症状，导致问题重复出现。

**根因**：急于完成验证，没有深入分析根本原因。

**规则**：失败时必须分析根因并修复，不使用临时补丁。

**示例**：
- ❌ 错误做法：发现空指针就加判空，不追溯数据来源
- ✅ 正确做法：追溯数据流，找到空值的来源并修复
```

## 使用流程

1. **每次执行 Skill 时**：先读取 `tasks/lessons.md`，回顾历史教训
2. **用户修正后**：立即更新 `tasks/lessons.md`，记录新模式
3. **定期回顾**：在执行关键任务前，快速浏览最近的教训

## 核心原则

| 原则 | 说明 |
|------|------|
| 立即记录 | 用户修正后立即记录，不要拖延 |
| 写出规则 | 不只是描述问题，要写出可执行的规则 |
| 包含示例 | 用对比示例展示正确与错误做法 |
| 避免责备 | 关注如何改进，而不是错误本身 |
| 持续回顾 | 每次执行前回顾历史教训，避免重复错误 |
